# Glossary

Plain-English definitions of the terms these guidelines use without stopping to explain them. Written for a developer who has built CRUD apps but not message-driven systems. Each entry ends with where the term first appears; "first used" counts the numbered chapters (the README's tables use many of these terms too, but it has no section numbers). The chapters are the authority — this file just gets you through them.

**Aggregate.** An entity — or a small cluster of entities saved together — that the code treats as one unit of change: load it, call a method on it, save it. In a CRUD app you'd update an `orders` row directly; here the `Order` class wraps that row in methods named after business actions (`Claim`, `Cancel`) which refuse illegal changes by throwing. The aggregate is also the transaction boundary: the default is one aggregate modified per transaction, guarded by its own version token (CON-1). First used in: ARCH-1.

**Anti-corruption layer.** A thin translation seam at the edge of a service that maps another service's message shapes into your own types before any business logic sees them. Its job is containment: when the other side's vocabulary is odd, or changes, you update one mapping in one place instead of chasing their type through your domain code. First used in: ARCH-5.

**At-least-once delivery.** The guarantee real message brokers actually give: your message will arrive, but it may arrive more than once — after a crash, a timeout, or an operator replaying it. A repeated arrival is called a redelivery. There is no practical exactly-once delivery, so every consumer must be written to survive seeing the same message twice; the guards for that are IDEM-1–IDEM-3. First used in: IDEM-1.

**Backing service.** Anything the app consumes over the network as part of doing its job — the database, the broker, a cache, a downstream API. Treated as an *attached resource*: reachable only through a configured address and credentials, so swapping the instance (a local container, staging, a failover replica) is a config change, never a code change. The flip side is that the process itself keeps no state worth keeping — whatever must survive lives in a backing service (RUN-1, RUN-2). First used in: RUN-1.

**Bounded context.** The boundary — typically one service and its database — inside which a model and its words have one exact meaning. "Order" in Billing and "Order" in Shipping may rightly be different types with different fields and rules; the boundary is what makes that safe rather than sloppy. Anything crossing the boundary goes through an explicit contract and translation (ARCH-5). First used in: ARCH-1.

**Command vs. event.** Two kinds of message with different ownership and rules. A command is an instruction aimed at exactly one handler, named imperatively (`ReserveStock`), and the receiver may refuse it. An event announces something that already happened, named in the past tense (`StockReserved`); any number of services may subscribe, and the publisher must not care who. The difference is load-bearing: a second subscriber to an event is free, while a second handler of a command executes the instruction twice — a bug. First used in: MSG-7.

**Correlation & causation ids.** Two ids that make an async workflow traceable. The correlation id names the whole business transaction — minted once, at the first edge, and riding unchanged on every message the workflow produces. The causation id names the one message that directly caused this one. Together they turn "grep five services and guess at the interleaving" into one log query that replays the chain in order. First used in: OPS-1.

**Concurrency token (optimistic concurrency).** A version column on a row that detects two writers colliding, without locks. Both writers read the row at version 7; each save says "update … where version = 7" and bumps it to 8. The first save wins; the second matches nothing, fails with a conflict, and must re-read fresh state and decide again. "Optimistic" because you assume collisions are rare and detect them, instead of locking up front. The full rule is CON-1–CON-2. First used in: ARCH-4.

**Dead-letter queue (DLQ).** The holding queue where the messaging framework parks a message it has given up on — after retries are exhausted, or immediately for poison. Nothing processes it further; a human investigates. These guidelines are emphatic that the DLQ is a diagnostic store only: an outcome the system understood and decided belongs in a domain row, never just in the DLQ (IDEM-5). First used in: ARCH-7.

**Domain event vs. integration event.** The same "something happened" fact wears two hats. A domain event is internal to one service: it drives local side effects (say, updating a read model) and can use rich private vocabulary. An integration event crosses to another service: it is a jointly-owned external contract, kept minimal, and changing it is a negotiation. Keep the two roles separately named even when one record temporarily serves both (ARCH-9). First used in: ARCH-3.

**Durable buffer.** Any place messages wait on disk rather than in memory: the outbox table, a broker queue, the dead-letter store, a scheduled-message store. A durable buffer converts an outage into a delay — but only if someone watches its depth (how many wait) and its oldest-age (how long the head has waited). First used in: OPS-5.

**Event sourcing.** A persistence style where you store the sequence of events that happened to an entity (`OrderPlaced`, `OrderPaid`, …) instead of its current-state row, and recompute current state by replaying them. These guidelines do not assume it: current-state rows are the ordinary case, and event sourcing is a per-case choice (ARCH-3) with its own disciplines if chosen (ARCH-4). First used in: ARCH-3.

**Eventual consistency.** Across services there is no shared transaction. Each service commits locally and tells the others by message, so for a moment their views disagree — they converge shortly after. The practical bite: a request your service accepted can still fail downstream, and that failure must come back as an explicit message your service reacts to, never be silently swallowed (ARCH-2). First used in: ARCH-2.

**Golden sample (drift gate).** A JSON file, committed by hand, holding the exact serialized form of one message — plus a test asserting today's code still produces and reads exactly that shape. It catches accidental contract drift: a renamed property, a serializer option silently flipping enums from names to numbers. When it fails, a human decides "intended change" or "regression"; it is never regenerated automatically. The mechanism lives in TEST-1. First used in: ARCH-5.

**Hazard window.** The span of time during which a duplicate of an operation can still arrive. At minimum it is the broker's redelivery window; at maximum it includes a dead-letter hand-replay months later. A dedup guard's retention must outlive the longest window it guards — that is the whole design rule. First used in: IDEM-1.

**Idempotency (and dedup guards).** An operation is idempotent when running it twice has the same effect as running it once. Most useful work isn't naturally idempotent (charging a card, reserving stock), so consumers add a dedup guard: a stored "I already handled message X" record checked before acting, with the database's primary key as the race-proof backstop. Frameworks ship a built-in version (a durable inbox) that covers a limited time window. The full treatment is IDEM-1–IDEM-3. First used in: ARCH-10.

**Message identity.** The stable name a message type travels and is stored under — e.g. a declared `"order-claimed.v1"` — instead of an identity derived from the class name. It is what lets you rename or move the class without orphaning copies of the message already sitting in queues, outboxes, or dead-letter stores. First used in: ARCH-5.

**Orchestration, choreography, and sagas.** Two ways to run a workflow that spans services. Choreography: no coordinator — each service reacts to the previous one's events, and the workflow's progress is read off the entities themselves. Orchestration: an explicit coordinator (called a saga or process manager) holds the workflow's state and directs the steps. A saga timeout is the coordinator scheduling itself a future "the reply never came" message, so a stuck workflow resolves instead of waiting forever (IDEM-8). The default here is choreography; orchestrate only when genuinely needed (ARCH-11). First used in: ARCH-11.

**Poison message.** A message that is structurally broken — malformed, incoherent, referencing something that cannot exist — so no number of retries will ever make it succeed. It signals a bug upstream. The route is: zero retries, straight to the dead-letter queue, a human investigates, and no business verdict is issued. Contrast with a business "no" (insufficient funds), which is a normal outcome to record and emit (IDEM-4). First used in: IDEM-4.

**Principal.** The authenticated identity performing an operation — a user, another service, an operator. Declaring the principal and the permission an operation requires is what separates "anonymous by decision" from "anonymous by accident". First used in: SEC-1.

**Read model (projection).** A separate, query-shaped copy of data — like a denormalized reporting table — kept up to date by a consumer (a projector) that listens to events or re-reads authoritative state, instead of by expensive joins at query time. It is derived and disposable; the write-side rows stay authoritative. The two projector styles and their different failure modes are ARCH-10. First used in: ARCH-2.

**Transactional outbox.** The pattern that makes "save the row and tell the world" safe. The handler does not publish to the broker directly; it writes the outgoing message as a row in the same database transaction as the state change, and a relay publishes it after commit. Crash before commit: neither the change nor the message exists. Crash after: the message sits safely in the table until relayed. The gap it closes — row saved but message lost, or message sent but row rolled back — is MSG-1. First used in: MSG-1.

**Ubiquitous language.** The discipline of writing code in the business's own words: one method per business action, named in the business's verbs (`Claim`, `Cancel`, `Expire`) — never a generic `SetStatus`. The payoff is that a domain expert can read a code review and spot a wrong rule, because the code says what the business says. First used in: ARCH-1.

**Value object.** A small immutable type defined entirely by its value rather than an id — `Money`, `DateRange`, an `Address`. Two value objects with equal fields are the same thing. They carry validation in their construction, so an impossible combination (a negative price, an end before a start) cannot be built at all (ARCH-6). First used in: ARCH-6.

**Vertical slice.** Organizing code by use case instead of by technical layer: one file (or folder) per feature, holding that feature's request type, handler, route registration, and error mapping together — rather than `controllers/`, `services/`, and `repositories/` folders that each hold a sliver of every feature. First used in: ARCH-7.
